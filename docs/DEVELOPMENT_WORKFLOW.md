# 开发过程与 AI 工作流说明

## 1. 分阶段协作方式

本项目没有使用“一条 Prompt 生成全部代码”的方式，而是先把测试题拆成 10 个可独立验收的阶段，并把当前版本保存在根目录 `AI_PANEL_STUDIO_PROMPTS.md`。实际开发由 Codex 工作模式执行；如果换成 Claude Code，流程不变：先读取公共约束和当前阶段 Prompt，只修改阶段范围内的文件，运行对应测试，人工核对结果，再创建独立 Git 提交。

应用运行时的模型通过 `LLMProvider` 隔离。测试和本地演示默认使用 deterministic Fake Provider；DeepSeek V4 Pro 或其他兼容 Chat Completions 的模型可以通过后端 `LLM_BASE_URL`、`LLM_MODEL` 和 `LLM_API_KEY` 接入。自动化测试不调用真实模型，这既避免成本和波动，也能准确判断失败来自业务实现还是模型输出。

开发过程依次采用：

1. **SDD**：先定义产品边界、状态机、SQLite 模型、REST/SSE 契约与需求追踪矩阵。
2. **DDD**：先用模拟数据验证演播厅的信息层级、三栏布局和响应式降级，再接真实 API。
3. **TDD**：先为非固定轮询、句数限制、会话隔离和异常复位写失败测试，然后实现编排器与模型契约。
4. **E2E**：用 Playwright 启动真实前后端，验证完整用户闭环和安全错误提示。

## 2. AI 上下文控制

对开发 AI 的上下文采用“文档事实源 + 当前阶段”的组合。数据结构和接口以 `docs/DATA_MODEL.md`、`docs/API_CONTRACT.md` 为准；AI 不需要从大量旧对话中猜测约束。每个阶段结束后更新 `docs/PROMPT_LOG.md`，只记录真实意图、问题和修正，不把自动生成的顺利过程伪装成工程经验。

应用中的虚拟专家也采用相同思想：每次模型调用只获得当前 Session 的主题、已确认身份、有限数量的公开 Transcript 和必要摘要。不同 Session 按 ID 查询和发布事件，不能共享全局 Transcript。模型只输出行动、紧迫度、公开关注点和最终发言，不请求、保存或展示隐藏思维链。

## 3. 实际遇到的问题与解决路径

### 问题一：API 使用了阵容 generation，但最初数据模型没有对应字段

在实现“重新生成后不能确认旧阵容”时发现，仅靠 Expert ID 无法可靠判断浏览器看到的阵容是否仍是最新版本。没有直接绕过检查，而是先把 Prompt 文档升级到 v1.1，在 Topic 上增加递增的 `panel_generation`，再补充过期 generation 返回 409 的测试。这样变更从需求、模型、API 到测试保持一致。

### 问题二：SQLite 读取时间后丢失时区信息

创建话题接口返回的时间带 `Z`，重新查询后 SQLite 返回 naive datetime，导致同一资源前后响应不一致。修复方式是在公开 Schema 边界统一把无时区时间解释为 UTC，而不是在前端忽略差异；对应回归测试比较创建和读取响应，确保 API 契约稳定。

### 问题三：同步 FastAPI 路由无法创建 asyncio 后台任务

首次为 `:start` 增加真实 API 测试时，`asyncio.create_task` 报告当前工作线程没有事件循环。原因是同步路由被 FastAPI 放入线程池。修复为异步路由，使讨论任务绑定到应用事件循环，同时在 lifespan 结束时取消和回收未完成任务。该问题如果只手动调用 DiscussionRunner 不会暴露，说明 API 级集成测试不可替代。

### 问题四：Windows 沙箱与中文用户名影响测试临时目录

Pytest 默认临时目录包含系统用户名，在受限环境中无法创建；Vite 在沙箱内解析真实路径也被拒绝。后端将 `basetemp` 固定到项目 `.tmp`，前端测试和构建在获批的本地执行环境中运行。这个调整只改变测试运行位置，没有降低测试内容或业务要求。

### 问题五：Fake Provider 掩盖了真实模型看不到字段契约

接入 DeepSeek 后，阵容生成连续返回 `PanelGenerationResult` 校验失败。原因不是环境变量，而是 Fake Provider 会直接构造正确字段，真实 Provider 却只收到 Schema 名称，没有收到字段、别名、数量和颜色格式。修复时先增加必然失败的测试，再统一向每次模型调用注入 Pydantic 导出的 JSON Schema；重试只反馈错误字段路径，既提高纠错成功率，也不把原始模型内容写入日志。

## 4. 对“工程化 AI 开发”的理解

工程化 AI 开发不是让模型一次写出看似完整的项目，而是把模型放进可验证的交付系统：明确契约、缩小改动范围、先写高风险测试、保留 Git 历史、把模型输出当作不可信输入，并在每个阶段通过自动化与人工观察共同验收。

本项目的关键控制点包括：Provider 可替换；Pydantic 对所有模型 JSON 做严格校验；失败重试有硬上限；API Key 只存在于后端环境；内部调度事件不进入 Transcript；结构化总结不直接进入 UI；SSE 事件先落库再发布；E2E 使用稳定 Fake Provider。AI 提高了实现和探索速度，但需求取舍、验收标准、异常边界和最终责任仍由开发者掌握。
